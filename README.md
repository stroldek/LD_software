# Lead Database Manager / ZAMOVO — v0.1.4

**Текущий тестовый этап:** подключение личного Telegram-аккаунта через MTProto (QR или номер телефона), мониторинг выбранных чатов, тестовая база лидов и экспорт в Excel.

## Что реализовано

| Блок | Возможности |
|---|---|
| **Личный аккаунт Telegram** | Вход по QR; альтернативный вход по номеру → коду → паролю 2FA. Аккаунт подключается отдельно от API-ключей приложения. Сессия хранится на сервере в зашифрованном виде. |
| **API-ключи приложения** | API ID и API Hash хранятся отдельно от сессии аккаунта. Один набор ключей можно использовать для входа в разные личные аккаунты. Выход из Telegram не удаляет ключи приложения. |
| **Мониторинг** | Выбор групп, супергрупп и каналов из диалогов подключённого аккаунта. Для канала читаются сообщения связанной группы обсуждения. Фильтры — ключевые слова; мониторинг по таймеру и вручную. |
| **База лидов** | Одна запись на Telegram ID, дедупликация сообщений, счётчик совпадений, поиск и постраничный просмотр. |
| **Excel** | Выгрузка имени, ника, телефона, источника, даты добавления и текста сообщения-триггера. Отсутствующий телефон обозначается `Nope`. |
| **Диагностика** | Проверяет конфигурацию Worker, D1, GramJS, WebSocket, MTProto-рукопожатие и получение QR-токена. |

В проекте нет Telegram-бота: не нужны BotFather, токен бота, Bot API webhook или регистрация webhook.

## Важные уточнения

**API ID / API Hash — это ключи приложения, а не аккаунта.** Они создаются на `my.telegram.org` в разделе API development tools. Затем пользователь отдельно выбирает личный аккаунт, который подключается через QR или номер. Эти два шага не обязаны выполняться с одного и того же аккаунта Telegram.

**Транспорт MTProto в Workers.** GramJS по умолчанию может выбрать IP-адрес DC, потому что Worker не имеет `window` и библиотека классифицирует runtime как Node. Для WSS в версии 0.1.4 принудительно используются доменные адреса Telegram DC (`pluto/venus/aurora/vesta/flora.web.telegram.org`). Диагностика теперь проверяет тот же DC4, что и стартовое подключение.

## Что не реализовано в этой версии

- Приложение только читает выбранные чаты. Отправка сообщений и авто-чат не включены.
- Нет глобального поиска пользователей Telegram и обхода ограничений приватности.
- Читаются только источники, доступные подключённому аккаунту и выбранные вручную.
- Телефон пользователя доступен только в случаях, когда Telegram разрешает его видеть.
- Сегменты, полноценный CRUD лидов, массовые операции, импорт и другие функции относятся к следующим этапам ТЗ.

## Что проверено

Автоматические тесты покрывают бизнес-логику входа, шифрование сессии, раздельное хранение API-ключей, сохранение ключей после выхода, маршрутизацию WSS DC, SQL и миграции. Тесты GramJS используют имитацию Telegram там, где реальный вход требует сетевого взаимодействия.

**Реальное MTProto-рукопожатие и QR-вход в опубликованном Cloudflare Worker пока не подтверждены.** Среда разработки не имеет доступа к реальному Telegram через Worker. После публикации нужно открыть вкладку «Аккаунт Telegram» → «Диагностика». Успешного WebSocket недостаточно: должны пройти пункты MTProto handshake и QR-token export.

## Обновление существующей базы D1

В версии 0.1.4 добавлена миграция:

`migrations/0003_account_credentials_no_bot.sql`

Её нужно выполнить **один раз после 0001 и 0002**. Миграция:
- переносит существующие зашифрованные API ID / API Hash в `tg_app_credentials`;
- очищает старые колонки API-ключей в `tg_account`;
- удаляет больше не используемые таблицы Bot API (`consent_events`, `telegram_updates`);
- сохраняет запись подключённого аккаунта и существующие лиды.

Подробности и порядок выполнения — в `migrations/README.md`.

## Развёртывание на Cloudflare

Все действия выполняются через браузер. Устанавливать Node.js, Python, Docker или Wrangler на компьютер пользователя для обычного использования не требуется.

1. В Cloudflare откройте Workers & Pages и выберите Worker, связанный с этим репозиторием.
2. Проверьте D1 binding `DB` и Durable Object binding `TG` по файлу `wrangler.jsonc`.
3. В D1 → Console последовательно выполните миграции `0001_stage1_prototype.sql`, `0002_live_telegram_test.sql` и `0003_account_credentials_no_bot.sql`. Уже применённые 0001/0002 повторно не запускать.
4. В Worker → Settings → Variables and Secrets добавьте secrets:
   - `ADMIN_TOKEN` — длинный пароль входа в панель (20+ символов);
   - `APP_SECRET` — секрет шифрования (24+ символов). Не меняйте его после сохранения сессии, иначе её нельзя будет расшифровать.
5. Откройте `my.telegram.org` → API development tools, создайте API-приложение и скопируйте `api_id` / `api_hash`.
6. Войдите в опубликованную панель, откройте «Аккаунт Telegram» и сохраните API-ключи приложения. Либо задайте их в Cloudflare secrets `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`.
7. Запустите диагностику. После успешных проверок нажмите «Показать QR-код» и сканируйте его в Telegram → Настройки → Устройства → Подключить устройство.

Секреты Bot API и настройка webhook больше не используются. Старые `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` и `SETUP_TOKEN`, если они ранее были добавлены в Cloudflare, можно удалить вручную.

## Структура проекта

- `public/` — интерфейс и клиентские библиотеки.
- `src/worker.js` — REST API Worker.
- `src/tg/` — движок пользовательской Telegram-сессии, GramJS-адаптер, Durable Object и D1 store.
- `migrations/` — последовательные SQL-миграции D1.
- `tests/` — unit-, API-, браузерные и SQLite-тесты.
- `docs/` — архитектура, Telegram-интеграция и инфраструктура.
